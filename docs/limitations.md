# Known limits

- **WordPress plugin headers identify declared plugin metadata.** Ravel reads the first 8 KiB of each candidate PHP file, following WordPress's header window. A source scan includes header-bearing files directly in the requested plugin directory. Recursive scans additionally discover conventional `wp-content/plugins/*.php`, `wp-content/plugins/*/*.php`, and `wp-content/mu-plugins/*.php` entries; deeper implementation files are excluded. OCI scans use those conventional paths after final-layer changes. Custom plugin directories, symlinks, plugin ZIP archives, themes, and WordPress core version detection are outside this collector's scope. At most 5,000 candidate headers are retained per image or repository scan. Header evidence hashes cover the inspected prefix, as indicated by `header-prefix-analysis` and the byte-range pointer; they are not full plugin archive hashes. Names and versions do not prove the files are unmodified, the plugin is active, or the package came from WordPress.org. Ravel leaves the PURL and distribution origin unset. Homepage and update URLs are not treated as download evidence. `Requires Plugins` is linked only when a unique normal plugin with that installation slug is observed in the same plugins directory; links remain conditional because activation and runtime hooks are unverified. Composer/npm dependencies are collected separately with `--all`.

- **Git provenance describes a checkout.** A local scan records the enclosing Git worktree's HEAD and dirty state; an untracked or modified input is not proven to match that commit. A remote scan fetches one explicit ref from a requested HTTPS, `ssh://`, or local file URL and records the resolved commit. The requested URL is not a verified upstream origin for every package. Remote scans skip submodules by default; `--git-submodules` includes pinned submodules up to three levels and 32 total when their URLs use the immediate parent's transport and host. Deeper gitlinks remain a coverage issue. Remote scans reject symlinks that escape the temporary checkout and cap total checkout size and entry count. Git LFS smudge and package-manager execution are disabled. Git LFS pointer files are reported as missing content in coverage; their referenced objects are not fetched. HTTPS authentication uses configured Git credential helpers; SSH uses configured keys or an agent and requires a known host key. Interactive prompts are disabled; scp-like SSH URLs are not accepted.

- **Repository runtime versions are declarations.** Version files and manifest ranges can select, suggest, or constrain a runtime, but a source checkout does not prove which runtime built or runs the application. Ravel keeps those semantics and source evidence in Ravel JSON. It does not evaluate version ranges, resolve aliases such as `lts/*`, or infer a runtime from source syntax. `.NET` `global.json` selects an SDK and may roll forward; it does not declare the deployed .NET runtime.
- **An inferred PURL does not prove a public-registry origin.** [PURL types](https://github.com/package-url/purl-spec/tree/main/docs/types/definitions) can define default public repositories. When a unique alternate registry is recorded for an occurrence, Ravel includes the standard `repository_url` qualifier. Without a registry record, a unique direct distribution URL or VCS source becomes `download_url` or `vcs_url`. Default public registry coordinates stay canonical where the location can be derived; direct mirrors and other recorded distribution locations are retained. Source qualifiers preserve existing platform, build, channel, classifier, and subpath information. `purlBasis: source_qualified` describes this construction, not independent verification of artifact provenance. CycloneDX includes standard `distribution`/`vcs` external references and comments; SPDX includes standard `sourceInfo` and uses a unique direct download URL or revision-specific VCS locator as `downloadLocation`. A registry base alone is not an exact package download URL. Multiple candidate download locations leave `downloadLocation: NOASSERTION` and retain all candidates in `sourceInfo`.
- **Missing source information cannot be reconstructed from a name alone.** Lock entries and installed metadata may identify an ecosystem package without recording its registry. Ravel retains an inferred coordinate with `purlBasis: ecosystem_inferred` and reports the origin limit where applicable. CycloneDX carries the supplemental `ravel:purlBasis` property; SPDX carries a package comment. Consumers ignoring these annotations can interpret an unqualified PURL as the default public package. Ravel does not turn a nearby `.npmrc` or `NuGet.Config` into proof of each artifact's source. Known local dependencies are not assigned public registry coordinates; an existing inferred coordinate is changed to a `generic` PURL when local metadata contradicts that assumption. Conflicting source candidates use a `generic` coordinate and report `purl_source_ambiguous` rather than selecting a registry arbitrarily. Packages without sufficient identity can still have no PURL. JSR packages are not relabeled as npm packages to fill the field; the current [PURL type index](https://github.com/package-url/purl-spec/blob/main/purl-types-index.json) has no JSR type.

- **Static data has boundaries.** SwiftPM pins and Gradle lockfiles do not contain complete dependency graphs. Go `go.mod` lists declared modules without proving the selected build list, and Go vendor data and Pub lockfiles do not establish every transitive edge. Maven POMs are not effective POMs, and Poetry/Composer manifest freshness is not verified.
- **Deno remote lock records do not establish reachability.** A `deno.lock` remote entry records a URL and integrity hash, but no import edges between remote modules. [Deno lockfiles can retain entries after imports are removed](https://docs.deno.com/examples/dependency_lockfile_tutorial/). Static scans include remote modules reached from a local source import or config mapping. With `--resolve --network allow`, Ravel fetches HTTPS remote source, checks its SHA-256 against the lockfile, and follows literal imports into locked remote modules or JSR/npm packages. The resolver is bounded to 512 modules, 2 MiB per module, 64 MiB total, and two minutes; it rejects private network destinations. Unreached lock records remain `lock_remote_reachability_unknown`. Computed imports and modules whose source cannot be fetched or verified remain partial coverage. Reported URLs have credentials and query parameters removed.
- **Some choices remain conditional.** Python markers and extras, npm peers, NuGet target frameworks, Cargo features and targets, and CocoaPods targets can require an environment or target selection. These edges remain in Ravel JSON and are omitted from unconditional standard-format dependency lists.
- **Installed OS databases do not prove repository origin.** Debian, APK, and RPM scans leave PURL and origin unset when the database cannot establish them. RPM installed headers provide dependency flags and versions. Ravel checks exact version offers using well-formed ASCII RPM EVRs, including epoch, release, letter and number segments, tilde, and caret; a requirement without a release compares against the provider's version. Range offers, missing dependency flags, and a provider's omitted release remain conditional. RPM file-path requirements use exact database ownership; ghost and missing-ok records, symlink aliases, and actual filesystem presence are not inferred from the database. A single unnested `(A if B)` or `(A if B else C)` requirement is evaluated when the guard's installed status can be established; other Boolean expressions remain unresolved. File ownership inspection is limited to one million records. APK v3 installed databases support plain ADB, legacy deflate, and custom deflate or zstd compression within a bounded input size.
- **Conda installed records identify an environment snapshot.** The JSON name, version, and build must match the `conda-meta` filename. A recorded HTTPS archive URL is emitted only when its filename and platform match the package and its path can be sanitized; it is marked `recorded_in_install_metadata`, not treated as a verified download. The channel, URL, and claimed archive digest do not prove that the distribution archive is present or that its files are unchanged, so actual origin remains unverified. Ravel emits an inferred Conda PURL with build/subdir and a sanitized channel when a matching artifact URL is recorded; a PURL does not verify that channel. Dependency strings and cross-ecosystem ownership are not yet resolved. Records are limited to 1 MiB each, 64 MiB and 10,000 files per image; skipped records appear in coverage.
- **Conan 2 lockfiles can retain alternatives.** Version 0.5 `conan.lock` can contain versions from multiple configurations and earlier resolutions. Ravel records each locked reference with `selection=unverified` and no dependency edge. Conan 1 version 0.4 graph nodes provide edges; build-context edges remain conditional. Neither lock format establishes a download repository or proves the binary package is present.
- **Mix lockfiles do not identify direct project dependencies.** Ravel parses literal `mix.lock` data without executing Elixir. Hex package identities, Git revisions, and local path declarations are recorded. Hex dependency aliases are linked conditionally because the lockfile alone does not verify each version constraint or whether the entry is enabled for a selected environment. Missing required aliases are reported; absent optional aliases are allowed. Private Hex repositories receive no default Hex PURL, and distribution origin remains unverified.
- **Legacy NuGet `packages.config` is a flat list.** It includes direct and transitive packages but contains no dependency edges or package source. Ravel links each listed package to the project without claiming it is direct, and leaves PURLs and origins unset. Per-entry `targetFramework` is an installation-time value, not proof of the project's current target; `allowedVersions` constrains updates but does not change the recorded installed version. The file does not verify that package bytes are present.
- **Cabal freeze captures solver choices, not installed bytes.** Ravel reads exact `==` package version constraints from `cabal.project.freeze`, including multiline lists. Constraints that say `installed`, set only flags, or use other expressions remain unresolved. The freeze file does not contain a package-to-package graph or a verified distribution source, and it may be stale relative to the current project manifest.
- **Stack lockfiles pin locations, not a selected dependency graph.** Ravel records immutable Hackage and Git entries from `packages` with `selection=unverified`. The `snapshots` list does not enumerate the project's actual dependencies. Unsupported package locations appear in coverage. A Hackage pin or Git commit in a lockfile does not prove that distribution bytes are present.
- **Julia manifests describe an environment, not verified installed bytes.** Ravel reads v1 and v2 package entries and links dependencies by UUID when the manifest supplies one. Name-only links to multiple UUIDs remain ambiguous. `Project.toml` or `JuliaProject.toml` supplies direct roots when present; weak dependencies and project extras remain conditional. A directory with multiple manifests requires a specific file because Ravel does not select a Julia runtime version. Versionless standard-library entries have no package version. Manifest freshness, registry selection, and distribution origin are unverified, so no registry PURL is asserted.
- **renv lockfiles record a restorable R library snapshot.** Ravel reads package names and versions, repository declarations, VCS remotes, and local paths. `Requirements` records packages needed in some way without the dependency category, so their edges are conditional. Older lockfiles can omit this field. The lockfile does not identify direct project imports or prove installed or distribution bytes. Its cache `Hash` is not an archive digest; Ravel does not export it as one. Repository labels alone do not establish a registry PURL.
- **sbt dependency lockfiles enumerate resolved modules per configuration.** Ravel reads version 1 `*.sbt.lock` entries, including test-only modules, without treating them as direct or inferring a dependency graph. A SHA-1 checksum is attached only when exactly one artifact is the default `<module>.jar`; other artifact checksums are not promoted to module hashes. The lockfile does not prove a repository or downloaded bytes, and may be stale relative to the build.
- **Rebar3 lockfiles flatten the selected dependencies.** Ravel parses literal v1.1/v1.2 `rebar.lock` terms without running Erlang, recording Hex pins and Git commit refs. The lock depth does not establish package-to-package edges. `pkg_hash` and `pkg_hash_ext` are left unrepresented until their exact artifact scope can be verified; package bytes and distribution origin remain unverified. Unsupported source forms appear in coverage.
- **Unified conda-lock files contain multiple target environments.** Ravel reads v1 Conda and Pip package entries for every listed platform, recording declared distribution URLs and valid SHA-256/MD5 checksums. It links unique same-platform package names conditionally because version constraints are not yet evaluated, and reports virtual packages such as `__glibc` separately. Direct project requirements, archive presence, and authenticated URL placeholders are not inferred. A recorded distribution URL supplies a source-qualified Conda or PyPI PURL; canonical official PyPI wheel locations can retain an unqualified PyPI PURL. Build and target details remain in the declared URL and platform/context fields when no structured qualifier is established.
- **Pixi locks separate package records from environment selections.** Ravel reads v6/v7 `pixi.lock` files and emits one occurrence for each selected environment and platform, including packages reused across environments. It records valid hashes, sanitized declared URLs, and relative local source paths, and emits source-qualified Conda/PyPI PURLs for recorded remote distributions. Canonical official PyPI wheel locations can retain an unqualified PyPI PURL; local source entries remain separate. Dependency links stay within the selected environment and platform and are conditional because version constraints and markers are not evaluated. A paired `pixi.toml` or Pixi-enabled `pyproject.toml` supplies name-matched direct Conda and PyPI requirements from default and named features, inline environments, and matching platform targets. For `pyproject.toml`, Ravel also reads `project.requires-python`, `project.dependencies`, optional dependencies, and dependency groups with `include-group` or self-extra references. Conda declarations override same-name native PyPI requirements; PEP 508 markers and version constraints are not evaluated. Unsupported manifest dependency categories, virtual packages, missing selections, and distribution bytes are reported as coverage limits.
- **Shards locks do not contain a transitive graph.** Ravel reads v1/v2 `shard.lock` records and declared Git, Mercurial, Fossil, or local sources. A paired `shard.yml` supplies direct and development dependencies. The lock does not prove transitive dependency edges, distribution bytes, or registry identity, so those claims remain absent or are reported as coverage limits.
- **OCI language coverage is still partial.** Installed Python dist-info, directory egg-info, and single-file egg-info metadata, legacy `requires.txt` dependencies, pip vendor manifests, setuptools' vendored dist-info metadata, CPython shared libraries under `/usr/local/lib`, Composer `installed.json` under default and configured vendor directories, .NET `*.deps.json` runtime manifests, conventional Node package manifests, pnpm virtual-store manifests reached by package symlinks, the Node.js `/usr/local/bin/node` ELF executable, installed Ruby gemspecs and CRuby shared libraries, installed R DESCRIPTION files, JAR/WAR files, and Go ELF build information are read. Legacy `requires.txt` extra and environment sections remain conditional; unsupported or oversized sidecars leave the graph partial. Other language packages and pnpm's global content-addressable store are not yet inventoried from image files. Unlinked pnpm virtual-store entries are reported instead of counted as installed packages. Pip's vendor manifest and setuptools' vendored metadata identify bundled versions but do not establish their internal dependency graphs or distribution origins. A .NET dependency manifest identifies the runtime's intended library graph. Ravel hashes managed DLL candidates found at conventional flat publish paths or RID-preserving `runtimes/<rid>/lib/` paths in the final image; their assembly identity, NuGet package version, and host RID selection remain unverified. Package source is also unavailable. Node package directory symlinks are followed only when they reach a recognized manifest within the final image; symlinked runtime executables, Java archives, Ruby gemspecs, R DESCRIPTION files, .NET dependency manifests, and candidate DLLs are not followed. Java archive inspection is capped at 128 MiB per file, 256 MiB per image, and 1,000 files. CPython and CRuby library inspection is capped at 32 MiB per file and 128 MiB per layer. Node.js executable inspection streams at most 256 MiB per file; installed version headers are capped at 64 KiB. Python egg-info requirements are capped at 256 KiB and 1,024 lines per file, and 8 MiB and 100,000 lines per image. Composer installed manifests are capped at 16 MiB per file, 64 MiB and 100 files per image. .NET dependency manifests are capped at 16 MiB per file, 64 MiB and 500 files per image, and 10,000 libraries per manifest. Managed DLL candidates are capped at 20 MiB per file, 128 MiB per layer, and 20,000 tracked paths per image. Ruby gemspec inspection is capped at 1 MiB per file, 64 MiB and 5,000 files per image. R DESCRIPTION inspection has the same limits; conventional `lib/R/library` and `lib/R/site-library` paths and literal absolute library roots in the OCI image configuration are read, and a `Built` field is required. Relative paths, R version tokens, and paths added by startup scripts are not resolved; an unsupported configured path is reported in coverage. A DESCRIPTION explicitly marked `Repository: CRAN` receives an inferred CRAN PURL; packages without a CRAN repository declaration are not relabeled as CRAN. The installed R runtime version, optional dependency activation, and actual package download origin are not inferred from DESCRIPTION files. Go ELF inspection keeps up to 64 MiB per file in memory and streams files up to 256 MiB through a temporary file, with a 512 MiB and 1,000-file limit per layer and 10,000 tracked files per image; skipped or malformed candidates appear in coverage.
- **PostgreSQL binary detection has a narrow scope.** Ravel reads only the final regular ELF file at `/usr/local/bin/postgres`, with a 32 MiB file limit. Its embedded `--version` and build strings must agree. Symlinked or nonstandard installations are not identified by this detector; the origin and dependency graph of a source-installed server remain unknown. Package-managed PostgreSQL is reported from its OS database record.
- **Redis binary detection has a narrow scope.** Ravel reads only the final regular ELF file at `/usr/local/bin/redis-server`, with a 32 MiB file limit. The Redis INFO and Docker build versions must agree, and a server version banner template must be present. This was checked on official Redis 7 and 8 Alpine images. Symlinked or nonstandard installations are not identified by this detector; distribution origin and dependency graph remain unknown.
- **Bun binary detection has a narrow scope.** Ravel reads only the final regular Linux ELF file at `/usr/local/bin/bun`, up to 256 MiB. The embedded banner and user-agent versions must agree, and the banner architecture must match the ELF. This was checked on official Bun 1.3 and 1.4 Alpine images. Symlinked or nonstandard installations are not identified by this detector; distribution origin and dependency graph remain unknown.
- **Deno binary detection has a narrow scope.** Ravel reads only the final regular Linux ELF file at `/bin/deno`, up to 256 MiB. Adjacent release and user-agent versions and their seven-character revision strings must agree; the ELF architecture must match the image. This was checked on official Deno 2.8 and 2.9 Alpine arm64 images and a Deno 2.8 Alpine amd64 image. Symlinked or nonstandard installations are not identified by this detector; distribution origin and dependency graph remain unknown.
- **Apache httpd binary detection has a narrow scope.** Ravel reads only the final regular Linux ELF file at `/usr/local/apache2/bin/httpd`, up to 32 MiB. The full and short `Apache/` versions must agree within 512 bytes in read-only data, and a server version output template must be present. This was checked on official 2.4.68 and 2.4.69 Alpine arm64 images and a 2.4.69 Debian Trixie arm64 image. Symlinked or nonstandard installations are not identified by this detector; distribution origin and dependency graph remain unknown.
- **HAProxy binary detection has a narrow scope.** Ravel reads only the final regular Linux ELF file at `/usr/local/sbin/haproxy`, up to 64 MiB. The embedded version and seven-character revision must agree between the build and benchmark strings, and the version output template must be present. This was checked on official 3.4.7 Alpine and 3.4.6 Debian Trixie arm64 images. Symlinked or nonstandard installations are not identified by this detector; distribution origin and dependency graph remain unknown.
- **Memcached binary detection has a narrow scope.** Ravel reads only the final regular Linux ELF file at `/usr/local/bin/memcached`, up to 32 MiB. The embedded command-line, usage, and wire-protocol versions must agree. This was checked on official 1.6.45 Alpine and 1.6.44 Debian Trixie arm64 images. Symlinked or nonstandard installations are not identified by this detector; distribution origin and dependency graph remain unknown.
- **micromamba binary detection has a narrow scope.** Ravel reads only the final regular Linux ELF file at `/usr/bin/micromamba`, up to 64 MiB. A micromamba command marker, libmamba user-agent version, and two adjacent build-version strings must agree. This was checked on `mambaorg/micromamba:2.5.0` for Linux arm64; its executable is not owned by a Debian package. Symlinked or nonstandard installations are not identified by this detector; distribution origin and dependency graph remain unknown.
- **PHP CLI and FPM binary detection has a narrow scope.** Ravel reads only the final regular Linux ELF files at `/usr/local/bin/php` and `/usr/local/sbin/php-fpm`, up to 64 MiB each. Their PHP 8 versions must agree with the Zend Engine 4 versions' minor and patch numbers. CLI and FPM have distinct required banner and FPM markers. An embedded mysqlnd version, when present, must also agree. This was checked on official PHP 8.4 Alpine and PHP 8.3 Debian Bookworm arm64 CLI and FPM images. PHP 7, symlinked or nonstandard installations are not identified by these detectors; distribution origin and dependency graph remain unknown.
- **Rust audit data is a build declaration.** Ravel reads the final regular ELF file's `.dep-v0` section, bounds its compressed and expanded data to 2 MiB and 8 MiB, and requires one root, valid package indices, and an acyclic graph. It excludes build-only crates in format 1 or newer. Format 0 cannot distinguish build-only dependencies and produces a coverage issue instead of package identities. Format 1 can still include unused runtime crates, especially in workspaces; Ravel marks its graph as declared and package origins as unverified. ELF files up to 64 MiB are inspected in memory; files up to 256 MiB are streamed through a temporary file. The shared ELF scan budget is 1,000 files and 512 MiB per layer, with at most 5,000 audit packages and 100,000 links per binary. Symlinked executables are not followed. This was checked against both uv executables in an Authentik arm64 image.
- **Debian system Node modules have two identities.** Ravel reads `package.json` directly below `/usr/share/nodejs/<name>` or `/usr/share/nodejs/@scope/<name>` and reports its module identity separately from the owning Debian package. When a final dpkg file list names the exact manifest and identifies one installed owner, Ravel links that Debian package to the module with file-list evidence. Missing, ambiguous, or size-limited ownership data remains visible as a coverage issue. A matching sibling manifest can settle an exact dependency version; ranges stay conditional. A module manifest alone does not prove an npm registry origin. This was checked against 25 dpkg-owned module manifests in a Jekyll build image. File-list inspection is limited to 1 MiB per list, 64 MiB per layer, and 10,000 lists per layer.
- **Ruby native gem compatibility needs a verified local platform.** Ravel accepts a literal ABI and architecture from the final `rbconfig.rb` only when it matches one verified CRuby runtime and the image CPU. It resolves the `x86_64` and `aarch64` Linux gem platform forms with GNU or musl libc semantics described by [RubyGems](https://github.com/ruby/rubygems/blob/master/lib/rubygems/platform.rb). Unsupported or ambiguous configurations leave native gem requirements unverified. The config file is limited to 256 KiB, and at most 16 configs are retained per image. Four native gem links in a Jekyll build image were checked against the image's RubyGems runtime.
- **Composer installed metadata is a registry snapshot.** The conventional vendor manifest establishes recorded package identity, not the presence of each package file or its distribution origin. Version constraints and virtual providers remain conditional. Ravel discovers custom vendor directories from a root `composer.json` only when the configured path is safe and local.
- **Composer file evidence is scoped.** A package-owned `composer.json` adds evidence only when its name matches the package recorded in `installed.json` and its `install-path` resolves to the conventional location inside the vendor directory. Whiteouts and replacements are applied before matching. Custom installer paths, symlinked manifests or parent directories, and other package files remain unverified. Package manifest reads are capped at 1 MiB per file, 32 MiB per layer, and 20,000 tracked paths; limits appear in coverage.
- **.NET runtime scope follows executable assets.** Older `.deps.json` files can include compile-only packages. Ravel omits non-root entries with no runtime asset and no path to one, while retaining metadata packages that connect an application to runtime assets. The omission is reported in coverage. This matches the intent of the [.NET 10 SDK change](https://learn.microsoft.com/en-us/dotnet/core/compatibility/sdk/10.0/deps-json-trimmed-packages); DLL candidates can have file digest evidence, while assets outside these conventional locations, RID fallback selection, and exact assembly-to-package identity remain unverified.
- **Standalone .NET DLL identity is file-scoped.** A PE VERSIONINFO product version and matching internal filename describe the observed assembly, not a NuGet package version or registry source. Ravel leaves its PURL empty and reports the missing dependency graph and origin. Managed DLLs without sufficient identity remain a coverage issue; localized resource satellites are skipped.
- **Some input versions are unsupported.** Binary `bun.lockb` is rejected; create a text `bun.lock` with Bun before scanning. Unknown lockfile versions and unparsed features are reported or rejected rather than silently guessed.

- **Image lockfiles supplement observed installations.** Source records and dependency links from a matching lock entry are declarations, not proof that the installed bytes came from that source. Lock-only entries do not create packages, lock hashes are not transferred to installed files, and correlated links remain conditional. npm occurrences must match lock paths; native gems and Conda packages must match their variant. Conflicting sources, multiple independent global-install projects, unsupported files and resource limits remain visible in coverage. See [image lockfile correlation](supported-inputs.md#image-lockfile-correlation) for supported inputs and standard-format annotations.
- **A PURL needs a defensible identity.** Verified runtime products use `generic` PURLs rather than unrelated names on a language registry. JARs need unambiguous Maven coordinates. An assembly version alone does not establish a NuGet package identity; an R base or non-CRAN package is not automatically a CRAN package, and WordPress headers do not establish a standard registry coordinate. These cases can still have an empty PURL. RPM PURLs require a recognized matching OS identity and preserve name case, architecture and epoch.
