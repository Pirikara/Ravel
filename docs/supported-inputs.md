# Supported inputs

The table describes inputs Ravel reads today. A listed format does not imply complete dependency or origin coverage; the report describes each scan's actual scope.

Repository directories also expose explicit runtime requirements from `.nvmrc`, `.node-version`, `.python-version`, `.ruby-version`, `.tool-versions`, `package.json` `engines.node`, `pyproject.toml` `requires-python` and Poetry's Python requirement, `go.mod` / `go.work` `go` and `toolchain`, Cargo `rust-version`, `rust-toolchain` / `rust-toolchain.toml`, `.NET` `global.json` SDK version, `Package.swift` tools version, and `pubspec.yaml` Dart/Flutter SDK constraints. These are declarations, not verified installed runtime versions.

An HTTPS or `ssh://` Git URL with `--git-ref REF --network allow` is fetched at one explicit revision into a bounded temporary checkout and scanned as a repository directory. SSH requires a configured key or agent and a known host key. A local `file://` Git URL works without network access. Local Git checkouts record their current commit and dirty state; exported trees have no Git claim. Remote scans can fetch pinned submodules up to three levels with `--git-submodules --all --recursive`; deeper gitlinks and package-manager resolvers remain outside this static scan. Git LFS pointers are reported as missing content; LFS objects are not fetched.

OCI scans accept OCI and Docker schema 2 media types, verify available descriptor SHA-256 hashes and uncompressed layer DiffIDs. A multi-image layout requires `--platform os/architecture[/variant]`. Legacy Docker save archives must contain one image. Registry references select `linux` on the host architecture by default and download only that platform's image; use `--platform` to override. The selected manifest digest is recorded in Ravel JSON.

## Image lockfile correlation

Image scans read final-layer lockfiles and selected companion manifests as supporting evidence for packages already found in installed metadata or executable/archive metadata. They do not add lock-only packages to the image inventory or treat lockfile integrity values as hashes of installed files.

Supported declarations include npm `package-lock.json`, `npm-shrinkwrap.json`, and `node_modules/.package-lock.json`; pnpm, Yarn Classic/Berry, Bun and Deno npm entries; uv, Poetry, PDM, Pipenv, pylock and pinned requirements; Bundler lockfile variants; Composer; NuGet lockfiles, assets files and `packages.config`; Cargo; Go `go.mod`; Gradle lockfiles, Maven dependency-tree JSON and sbt locks; renv; conda-lock and Pixi v6/v7. Relevant `package.json`, `pyproject.toml`, `Cargo.toml`, `pixi.toml`, `go.work` and Deno configs are staged with the declarations. Requirements includes are restricted to the staged image tree; common `requirements*.txt` names and `requirements/` text files are retained. Locks bundled inside installed dependency source trees are excluded, apart from npm’s installed hidden lock index. No package manager or image code runs during a scan.

Matching requires ecosystem, name and version agreement. npm package-lock entries also require the installed occurrence path to agree. The nearest containing project takes precedence. Global Python, Ruby, R, Conda, Go and Cargo installations can correlate with a single project scope and one observed installation environment for the matching coordinate; multiple independent projects or conflicting source candidates remain unresolved. Native gem platforms and Conda build/subdir identity must agree. pip/setuptools vendored packages are excluded from application-lock matching.

Matched source records use `correlated_from_lockfile`; their evidence points to the lockfile's final layer and content digest. Correlated dependency links connect matched installed occurrences, retain existing conditions, and add `lockfile_installation=unverified`. Image installed edges remain installed edges; project roots are not promoted to direct image dependencies. A matching name/version does not prove artifact provenance or runtime activation.

Ravel JSON retains these records directly. CycloneDX component properties and SPDX package comments retain `ravel:lockfileEvidence`, `ravel:lockfileOrigin`, and `ravel:lockfileDependency` as JSON values. `ravel:occurrence` identifies the Ravel occurrence referenced by these annotations. Conditional lock links are annotations rather than unconditional standard-format dependencies. Installed source records from npm `_resolved`, Composer source/dist fields and Python `direct_url.json` are read before lock correlation. Their URLs are sanitized and marked `recorded_in_install_metadata`; `ravel:installedOrigin` annotations preserve these records in CycloneDX/SPDX. Archive hash claims in these records do not become hashes of installed files. Python direct URL records are limited to 64 KiB; local-directory records do not expose the build machine’s path.

Each image retains at most 256 project/source-sidecar files, 8 MiB per file and 64 MiB total; parsed declarations are limited to 50,000 components and 200,000 edges. Deleted/opaque-layer entries are removed, unsupported symlinks are reported, and skipped, invalid or ambiguous inputs appear in coverage.

### Source identity in standard formats

Known alternate registries use the standard PURL `repository_url` qualifier. Unique direct distributions and VCS sources use `download_url` and `vcs_url` when no registry identity is recorded. This applies to lockfile scans and matching installed image packages. Public defaults remain canonical where derivable. Qualifiers describe recorded sources; they do not authenticate the registry or verify downloaded bytes.

CycloneDX exports recorded registries and distributions as standard `distribution` references and VCS sources as `vcs` references, with their source status in reference comments. SPDX exports `sourceInfo` and a unique exact distribution or revision-specific VCS location as `downloadLocation`; a registry base or ambiguous set of locations remains `NOASSERTION`. Ravel's existing properties and package comments supplement these standard fields. Unknown origins still use inferred ecosystem coordinates where supported; `purlBasis` remains a Ravel extension. See [limitations](limitations.md) before treating an inferred coordinate as a public-registry identity.
